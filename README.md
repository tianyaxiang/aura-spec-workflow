# aura-spec-workflow

A Claude Code plugin that adds a Kiro-style SPEC workflow (requirements / design / tasks) with **auto-surface on session start**. The point is: a new Claude session can pick up where the last one left off without you having to remind it.

English · [中文](./README_zh.md)

---

## One-minute mental model

The plugin does two things:

1. **Every Claude session, it auto-injects unchecked items from `docs/specs/*/tasks.md`** — Claude knows where you left off without you saying anything.
2. **Two slash commands**: `/aura-spec-workflow:spec <name>` starts a new spec; `/aura-spec-workflow:spec-status` shows progress on demand.

Four roles you should distinguish:

| Role | Who | When |
|---|---|---|
| 🤖 **SessionStart hook** | Plugin | Fires automatically on every session start / `/clear` / compact — no input needed |
| ⌨️ **Slash command** | You | You type `/aura-spec-workflow:spec <name>` or `/aura-spec-workflow:spec-status` |
| 💬 **Fill content** | Claude in conversation | You describe what you want → Claude writes the three .md files; or you write by hand |
| ✏️ **Update status** | Claude (default: automatic) / you (manual) | Claude auto-flips `[ ]` to `[x]` after finishing a task (driven by a convention the SessionStart hook injects); you can also hand-edit or say "mark #N done" |

Key insight: **the plugin only handles "surface state" and "scaffold". The actual spec content is written by you and Claude together, not generated by the plugin out of thin air.**

## Workflow at a glance

Breaking down "feature from idea to shipped" into 7 stages, with who-does-what:

| # | Stage | What you do | What the system / Claude does |
|---|---|---|---|
| 1 | Start a spec | Type `/aura-spec-workflow:spec <name>` | Plugin scaffolds `docs/specs/<name>/{requirements,design,tasks}.md` from templates |
| 2 | Fill requirements | In plain language: "I want X, for users Y, success means Z. Write it to requirements.md" | Claude structures the conversation into user stories + acceptance criteria, writes to file |
| 3 | Fill design | Tell Claude to enter plan mode ("think first, code later"), then "write the plan to design.md" | Claude runs Explore subagents on the code, writes components table / data model / sequence / risks |
| 4 | Break into tasks | "Break design.md into 10–20 tasks, each finishable in 1–2 hours, with acceptance hints" | Claude proposes the numbered list; you review and tweak |
| 5 | Execute | Say one at a time: "do #1" (or "do next" — Claude pulls from spec-status) | Claude edits code, runs tests, maybe commits |
| 6 | Mark done | **Usually nothing to do** — Claude auto-flips the checkbox; or hand-edit `[ ]` → `[x]`, or say "mark #1 done" | Claude calls the Edit tool on tasks.md (guided by the convention the SessionStart hook injects) |
| 7 | Continue (next session) | **Type nothing.** Just read the injected context | 🤖 SessionStart hook tells Claude "next: #2 xxx" automatically |

## End-to-end walkthrough (real example)

Using `watchlist-extension` from the aura project. Lines starting with `>` are **your input**; `📋` is **auto-injected by the system**; everything else is Claude's response.

### Step 1: Start the spec

```
> /aura-spec-workflow:spec watchlist-extension

[Claude runs Bash mkdir + cp, then replies]
Created:
  docs/specs/watchlist-extension/requirements.md
  docs/specs/watchlist-extension/design.md
  docs/specs/watchlist-extension/tasks.md
Suggested fill order: requirements → design → tasks.
```

The three files are now empty templates.

### Step 2: Fill requirements (conversation-driven)

Don't let Claude guess. Talk it through, then have it write:

```
> I want to add 9 fields to watchlist: custom display name, target buy/sell price,
  alert change %, note, plus 3 alert toggles (master / on buy hit / on sell hit).
  Goal: users get targeted WeChat alerts, not just generic up/down notifications.

> Turn this into user stories + acceptance criteria and write to
  docs/specs/watchlist-extension/requirements.md.

[Claude writes the file, reports the path]
```

If you already have a complete spec document, **you can hand-write requirements.md** and skip this step.

### Step 3: Fill design (plan mode + Claude-driven)

With requirements clear, have Claude investigate the code before writing the design:

```
> Enter plan mode. Read the existing watchlist model / push pipeline / frontend table
  in aura, then design how to extend with minimal disruption.

[Claude EnterPlanMode, runs Explore subagent, presents approach]
[You review, maybe push back on a few points, Claude ExitPlanMode]

> Write that plan to docs/specs/watchlist-extension/design.md.
  Use real file paths in the components table. Add a sequence diagram for the alert scan flow.
```

### Step 4: Break into tasks (Claude proposes, you review)

```
> Break design.md into tasks. Each should be 1–2 hours of work with an acceptance hint.
  Order by dependency, bottom-up. Write to tasks.md.

[Claude lists - [ ] 1. ... - [ ] 18. ...]

> Swap #3 and #4 order. Change #15 to "browser walkthrough UI, no code changes".
```

### Step 5: Execute (one task at a time)

```
> Do #1.

[Claude edits code, runs tests, maybe commits; then auto-flips "- [ ] 1. ..." to "- [x] 1. ..." in tasks.md]

> Do #2.
…
```

**About auto-marking**: After finishing a task, Claude flips the checkbox by default — that convention is injected by the SessionStart hook. If Claude forgets, or you only finished partially (leave `[ ]` + add a one-line note), hand-edit or say "mark #N done".

Or, more concise:

```
> Check spec-status. Do the next item.
```

Claude runs `/aura-spec-workflow:spec-status` first to get "next", then does it.

### Step 6: Continue — the next session after `/clear`

This is the plugin's whole point. New session, first second, **you type nothing**. The system has already injected:

```
📋 Active SPECs in this repo:
  • watchlist-extension  (14/18 done)  next: 15. browser walkthrough WatchlistPage UI...

Open docs/specs/<name>/tasks.md to update. Run /aura-spec-workflow:spec-status anytime.
```

You just say:

```
> Continue.
```

Or:

```
> For #15, list a UI walkthrough checklist.
```

Claude already knows what #15 is. No re-introducing watchlist-extension.

### Step 7: All `[x]` — wrap up

```
> Spec is complete. Move the done items in tasks.md to the bottom "Done" section,
  clear Open.
```

Or just leave them in place — git log is the audit trail.

## Four day-to-day patterns

### Pattern A: Add a task mid-flight

You're on #5, you realize you also need to do #19. **Never renumber.** Append to the end:

```
> Add a new task at the end of tasks.md: "- [ ] 19. Add retry on quote fetch, guard against flaky network".
```

### Pattern B: Requirements changed

Edit requirements.md directly. **git diff is the change log.** No need for "requirements v2". For big shifts, add a `## Change log 2026-05-21: ...` section at the top of design.md.

### Pattern C: Multiple parallel specs

One directory per feature. The SessionStart hook lists every spec that still has unchecked items:

```
📋 Active SPECs in this repo:
  • watchlist-extension  (14/18 done)  next: 15. browser walkthrough...
  • auth-rewrite         (3/12 done)   next: 4. add refresh token rotation
```

### Pattern D: Check progress

```
> /aura-spec-workflow:spec-status
```

Same output as the SessionStart hook, available any time.

| Check progress | `/aura-spec-workflow:spec-status` |
| Add ad-hoc task | "Append to tasks.md: - [ ] N. xxx" |

## Conventions

- One spec per feature or bugfix. Keep scope small — finishable in days, not weeks.
- Task IDs are stable. **Never renumber.** Add new tasks at the end.
- Scanner counts only `[ ]` and `[x]`. `[~]` is a local "in progress" marker that doesn't count.
- Every task should be self-contained — a future session reading just `tasks.md` should understand what to do.
- Changed requirements → edit `requirements.md` directly. git diff is the history. No "v2" files.

## Troubleshooting

| Symptom | Check |
|---|---|
| New session doesn't show 📋 Active SPECs | `docs/specs/` doesn't exist, all specs are fully `[x]` (hook is silent by design), or the plugin isn't installed (`/plugin` → Installed tab) |
| `/aura-spec-workflow:spec` not recognized | `/reload-plugins`; if still missing, `/plugin` → Errors tab |
| Skill reports "file not found" | Plugin paths used relative paths or didn't use `${CLAUDE_PLUGIN_ROOT}` — fix and `/reload-plugins` |
| Hook output garbled / errors | Run the script directly: `CLAUDE_PROJECT_DIR=$PWD ~/.claude/plugins/cache/.../bin/spec-status.sh` (find the cache path via `/plugin` → details) |
| Want to see exactly what the hook injects | Start Claude Code with `--debug`; SessionStart output goes to stderr |
